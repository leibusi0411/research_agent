# Use Context Builders and typed role schemas

Research roles will receive typed inputs built by centralized Context Builder functions such as `build_planner_context(task_id)`, `build_executor_context(task_id, subtask_id)`, `build_supervisor_context(task_id)`, and `build_curator_context(task_id)`. Each role will use explicit Pydantic-style input and output schemas so nodes do not hand-roll state access or exchange unconstrained free text, Planner output becomes structured Blackboard data rather than Markdown prose, Supervisor routing must come from structured `SupervisorOutput` rather than parsed prose, and Curator output must be grounded in findings, evidence, and source records. V1 `SupervisorOutput.route` is limited to `continue_execution`, `revise_plan`, `curate`, or `fail`; failed LLM schema validation gets at most two repair attempts before the Web Research Workflow fails. Planner and Curator each get up to two repair attempts; Supervisor gets up to two repair attempts, and if all fail the runtime routes to `fail`.

Planner is the same LangGraph node for initial planning and Plan Revision. Initial `PlannerInput` contains `original_question`. Revision `PlannerInput` contains `original_question`, `current_plan`, `executor_outputs`, `research_gaps`, and `plan_revision_request`, while output remains the same PlannerOutput schema.

`PlannerOutput` contains `research_title: str` and proposed subtask questions. The implementation schema may represent each proposed question as `PlannerSubtaskDraft` with only `question: str`; Planner must not output subtask IDs, status, or goal. Initial Planner prompts ask for 3-5 subtask drafts, and Plan Revision prompts ask for 1-3 new subtask drafts; these are prompt constraints rather than runtime hard limits. In v1, the research plan is the runtime-normalized subtask list, and Plan Revision appends new `pending` subtasks based on Supervisor-maintained research gaps and prior executor results. The Supervisor may also mark existing pending subtasks as `skipped` via `SupervisorOutput.skip_subtask_ids` before requesting plan revision, allowing the Planner to focus on productive directions without being blocked by subtasks that have been judged unproductive; skipped subtasks are not executed and do not count toward retrieval round limits. PlannerOutput does not include `max_retrieval_rounds` or other hard runtime limits because those come from configuration and are enforced by the runtime and Supervisor.

`ResearchSubtask` contains `subtask_id`, `question`, and `status: pending | completed | failed | skipped`. Runtime owns `subtask_id` and initial status assignment for both initial planning and Plan Revision, using stable IDs such as `st_1`, `st_2`, and the next available number for appended subtasks. Planner proposes questions; runtime normalizes them into `ResearchSubtask` records with `pending` status, and later status updates come from ResearchExecutor results or Supervisor skip decisions. V1 does not include a separate `goal` field because `question` is the execution target, while completion is determined by the ResearchExecutor during its tool loop and returned as `ExecutorOutput.status`.

`ExecutorOutput` represents the result of one isolated subtask run, not the whole ResearchExecutor node invocation. Its v1 fields are `subtask_id: str`, `status: completed | failed`, `findings: list[Finding]`, `sources: list[WebSource]`, and `failure_reason: str | None`. When the ResearchExecutor node runs multiple selected subtasks concurrently, the node returns `executor_outputs: list[ExecutorOutput]`, then merges each result into the Blackboard. ExecutorOutput does not include gap suggestions, raw source text, tool raw results, or scratchpad content.

`Finding` fields are `finding_id: str`, `subtask_id: str`, `text: str`, and `source_ids: list[str]`. V1 uses this lightweight finding-to-source relationship instead of a separate claim/evidence-set model. Runtime assigns `finding_id` values using the task-local `f_1`, `f_2`, and so on sequence.

`WebSource` fields are `source_id: str`, `title: str`, `url: str`, and `fetched_at: datetime`. Runtime assigns `source_id` values using the task-local `src_1`, `src_2`, and so on sequence. V1 does not perform URL deduplication during execution, so repeated URLs may receive separate source IDs; the Curator output stage merges duplicate URLs into a single source entry in the final report. `fetched_at` uses UTC ISO 8601 with `Z`. WebSource is metadata only; full extracted source text is stored as a Web Source Snapshot task artifact.

`SupervisorInput` contains `original_question`, `current_plan`, and `executor_outputs`. `current_plan` includes the Planner-created subtasks and their current statuses, so Supervisor can see the original plan and which subtasks are pending, completed, failed, or skipped. `executor_outputs` contains structured per-subtask results, including status, findings, Web source metadata, and failure reasons. Supervisor does not read full source snapshots, tool raw results, or executor scratchpads.

`SupervisorOutput` fields are `route: continue_execution | revise_plan | curate | fail`, `reason: str`, `next_subtask_ids: list[str]`, `skip_subtask_ids: list[str]`, `plan_revision_request: str | None`, `research_gaps: list[str]`, and `saturation: bool`. `research_gaps` is the complete Supervisor-maintained list of missing-information notes after the current review, not a partial patch or a structured object with blocking or severity fields. It is workflow-internal context for continuing execution or revising the plan, not final report content. The graph routes only by `route`; `saturation` is an explanation and audit field indicating whether Supervisor believes more Web Research is unlikely to materially improve the output. Supervisor owns Research Gap creation and maintenance because it has the global view across the original question, plan, subtask statuses, findings, sources, and failures. It does not call tools, write the final report, create plans directly, or decide the fine-grained completion state of an individual subtask. Runtime hard limits such as maximum retrieval rounds are enforced by the graph/runtime layer rather than passed into the Supervisor prompt as counters.

`CuratorOutput` fields are `title: str`, `summary: str`, `findings: list[Finding]`, and `sources: list[WebSource]`. Curator receives the user question, title, findings with `source_ids`, and Web source records, then returns this final structured report content for Markdown rendering. It must not add new sources, cite Local Results, call tools, introduce findings that are not present in the Blackboard, or include workflow-internal research gaps in the final report.
