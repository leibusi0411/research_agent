# Use a single ResearchExecutor for v1

Because Web Search, Web Fetch Extract, Web PDF Download, and related operations are exposed through the runtime Tool Gateway, Web Research can use a single ResearchExecutor LangGraph node type for Supervisor-assigned subtasks rather than separate tool-specific executor nodes.

A ResearchExecutor node invocation receives Supervisor-selected subtask IDs from the Blackboard and may execute multiple subtasks concurrently. Concurrency is limited by `research.max_concurrent_subtasks`, defaulting to `3`; if Supervisor selects more subtasks than the limit, ResearchExecutor executes them in batches. Each subtask execution is an isolated executor agent run with its own scratchpad and internal tool loop: call a tool, append the structured result to that subtask's temporary executor context, then decide whether the subtask is complete, needs another tool call, or should return Subtask Failure. Subtask completion judgment belongs to ResearchExecutor and is returned as `ExecutorOutput.status`. Subtask scratchpads do not communicate with each other directly. Each subtask execution returns one `ExecutorOutput`; the ResearchExecutor node returns `executor_outputs: list[ExecutorOutput]`. When all selected subtask runs finish, ResearchExecutor merges structured outputs such as findings, sources, statuses, and failure reasons back into the Blackboard. The Supervisor context builder passes the current plan and full structured `executor_outputs` to Supervisor for routing, while excluding full source snapshots, tool raw results, and executor scratchpads. ResearchExecutor does not create or suggest Research Gaps; Supervisor performs that reflection step using its focused global view.

Local RAG remains a fixed retrieval display flow, while Web Research keeps execution logic simple and preserves workflow-boundary checks and structured tool-call recording in the gateway.
